Wataniya ETL demo

NiFi already moves Kastle and Avaya into SQL Server and builds the warehouse. This demo runs one of those rules in Python: copy EMPLOYEE as-is into PostgreSQL, then let SQL build the staging table and the employee dimension, with a run log you can open.

The difference

The employee rule is the same. The path around it is not. NiFi chains processors with flowfiles. The new job is two API calls, a raw copy, and SQL files in order.

NiFi today — the full estate

  1. Two sourcesOracle Kastle, many tables in PULSE_NFC_PROD. Avaya KPIVision, four call and agent views.
  2. A view supplies the windowDATE_PARAM_VW holds the start and end. Kastle starts at 12:30. Avaya repeats every 15 minutes from the latest fact timestamp.
  3. Each table is its own groupTruncate SQL Server STG, read the source, stamp PG_NAME, LD_STRT_DT, and EXE_ID, then insert. Rows move as Avro flowfiles.
  4. A funnel does not waitEach finished branch can start the warehouse. The facts can run once per branch, not once after every table has loaded.
  5. SQL lives inside processorsDimensions insert a version open until 9999-12-31, then close the previous row. Facts delete that window and insert the aggregate into Wataniya_DWH.
  6. Avaya also refreshes a cubeFour facts load, and a separate processor starts the SSAS job every 5 minutes. The trace of a run is NiFi provenance.

Python job — EMPLOYEE only

  1. One HTTP call starts the workFastAPI takes one job at a time and returns a run id. A second call while it is running gets 409.
  2. Extract is a copyOracle EMPLOYEE, filtered on MAKEDATE, lands in PostgreSQL raw.employee. No technical columns are added to the row.
  3. Transform is SQL, one layer at a timeThe call passes layer: staging, dimension, or fact. Python splits the file name on __, takes the number, and runs that layer in that order. V1__stg_raw_employee.sql is first. V2__dim_employee.sql is next, with no source schema because the source is already in the warehouse.
  4. Same dimension rule, new schemaV1__stg_raw_employee.sql builds reportingdw.stg_employee from raw.employee. V2__dim_employee.sql builds reportingdw.dim_employee. The latest row stays open at 9999-12-31.
  5. The run is the audit trailEvery step is a line in logs/etl-YYYY-MM-DD.log and a row in etl.run_event. You poll GET /runs/{run_id}.
  6. The other tables are in the map belowKastle, Avaya, the dimensions, and the facts are listed. Only raw.employee, stg_employee, and dim_employee have a load today. The rest wait for their SQL file.

Where rows land

NiFi writes SQL Server STG, then Wataniya_DWH. Python writes PostgreSQL raw, then reportingdw.

Who shapes the row

NiFi shapes rows in processors and carries them as Avro. Python copies the source. The SQL file does the rest.

How you prove the run

NiFi uses canvas provenance. Python gives you a run id, a daily file, and etl.run_event.

Extract and load, in the order it happens

POST /jobs/extract with job, start_dt, and end_dt. The end date is included, even when MAKEDATE has a time.

Yellow — source Green — PostgreSQL Blue — what you click Gray — the run log Red — stop or failure
  1. RequestBody is {"job":"employee","start_dt":"2026-06-01","end_dt":"2026-06-30"}. Change the dates to the window you want to show.
  2. GateAn unknown job returns 404. A job that is not enabled returns 409. If any ETL job is already running, this call returns 409 and creates no run.
  3. Run row, then 202The API inserts etl.run as queued and returns run_id. The load continues after the response.
  4. Oracle readSELECT * FROM PULSE_NFC_PROD.EMPLOYEE where MAKEDATE is on or after the start date and before the day after the end date. The log records the connect and the columns. The password is not logged.
  5. Create raw.employee the first timeText for character data, numeric for NUMBER, timestamp for dates. Names are lowercased. If the table already exists with a different column list, the run fails instead of loading into the wrong shape.
  6. Replace the windowTruncate raw.employee, then COPY in batches of 5,000. Each batch logs its size, the running total, and how long it took.
  7. Close the runStatus becomes success, or failed with the error. The lock is released either way. raw.employee holds this window only.
  8. What you showRefresh GET /runs/{run_id} until status is success. Read the connect line, the column list, the truncate, the batches, and the committed row count. The same text is in the daily log file.
  9. Do not continue on a failed extractTransform reads raw.employee. If this run failed, stop the demo here and show the error on the run.

Transform and load, in the order it happens

POST /jobs/transform with layer and the same two dates. Call staging first, then dimension. Each call is a new run id. Python executes that layer's SQL.

  1. RequestBody is {"layer":"staging","start_dt":"2026-06-01","end_dt":"2026-06-30"}. Repeat with "layer":"dimension" after staging succeeds. The one-job lock applies to each call.
  2. Hand the dates to SQLThe runner sets session values etl.start_dt and etl.end_dt. The file reads them with current_setting.
  3. Files in version orderstaging runs V1__stg_raw_employee.sql. dimension runs V2__dim_employee.sql. fact has no file yet, so that call logs an empty layer and finishes.
  4. Staging copy — statements 1 to 3Create reportingdw.stg_employee like raw.employee, truncate it, and insert every raw row. Staging is still the extract.
  5. Dimension table — statements 1 and 2This is the dimension call. employee_sk is an identity key. The business codes are text. start_dt and end_dt are dates. Unique on employee and start date.
  6. Latest row in the window — statement 3One row per employeeid, the latest makedate. end_dt is 9999-12-31. If that version is already loaded, it is skipped, so running the demo twice does not stack duplicates.
  7. Close the previous open version — statement 4Among rows still open, the older end date becomes the day before the next start date. The newest row stays open. This is the NiFi employee rule.
  8. If a statement failsThat statement rolls back. Earlier statements in the file stay committed. The sequence stops, the run is failed, and the log has the statement text and the database error.
  9. What you showThe staging run has three statement lines. The dimension run has four. Then count raw.employee, reportingdw.stg_employee, and reportingdw.dim_employee. Staging should match raw. The dimension should show one open row per employee from this window.

Click this, in this order

  1. Open http://127.0.0.1:8000/docs and show GET /health returning status ok.
  2. Show GET /jobs. employee, V1__stg_raw_employee, and V2__dim_employee are enabled.
  3. Send POST /jobs/extract. Copy the run_id.
  4. Send GET /runs/{run_id} until status is success. Scroll the events.
  5. Send POST /jobs/transform with layer set to staging and the same dates. Poll that run id.
  6. Send POST /jobs/transform again with layer set to dimension. Poll that run id.
  7. Show the three staging statements and the four dimension statements, then the three table counts.
